## Member activation correction

The hosted `private.complete_member_setup` definition selects only provisioning state `provisioned`, while `attach_provisioned_member` records an unconfirmed new account as `awaiting_verification`. Email verification does not update that application row. A new isolated SQL regression reproduced failure even after verified email, a personal password change and a fresh provider session.

The proposal accepts either pending state while retaining every existing check: current authenticated identity, exact organization membership, provisioned/setup-required lifecycle, required password change, credential expiry, independently confirmed email, protected provisioning marker, changed provider password fingerprint and a new trusted Auth session. Tests still deny unverified email, unchanged passwords, stale sessions, unauthorized roles, foreign organizations and anonymous calls; activation/removal retains source and learning history.

The Auth adapter creates only an unverified identity with a protected operation marker. It never adopts or resets an unrelated identity and never sends an invitation. Two-seat reservation and failure/retry handling remain in the existing atomic RPCs. The application exposes only explicit one-time passcodes in the owner action response; credentials are not persisted in app storage or placed in URLs. Server Auth requests are bounded, and publishable/anonymous keys cannot enable the admin adapter.
